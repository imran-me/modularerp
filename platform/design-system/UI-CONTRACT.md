# UI CONTRACT — the universal look of the whole ERP

> **Scope: EVERY company, EVERY module, forever.** Group cockpit, Travels, Woodart
> Interiors, IT, Shop, Construction — one nav bar, one page head, one card, one
> button. If a screen invents its own version of anything on this page, that
> screen is wrong, not the contract.
>
> **Owner rule (2026-07-27):** *"Always save styles, or types, so it applies
> universally — like the nav bar, all same everywhere."* This file is where that
> is saved. It is a CONTRACT, not a suggestion.

---

## 0 · The one-line rule

**A module never authors chrome. A module authors its own body, and only its body.**

Chrome = the app shell (rail, sidebar, topbar), the page head, the section-tab
band, cards, KPI tiles, buttons, badges, tables, modals, forms, empty states.
All of it already exists, is themed for light + dark, and is shared. Reuse it.

---

## 1 · Ownership map — who is allowed to change what

| Layer | Lives in | Who may edit it | A module may… |
|---|---|---|---|
| **App shell** — rail · sidebar · nav · topbar | `platform/core/app.js` + `css/layout.css` | platform only | …nothing. Never touched by a module. |
| **Design tokens** — colour, type scale, radius, shadow, motion | `platform/design-system/css/tokens.css` | platform only | …*read* via `var(--…)`. Never hard-code a hex. |
| **Component classes** — `.card` `.btn` `.kpi-card` `.tbl` `.modal-*` … | `platform/design-system/css/components.css` | platform only | …*use* the class. Never redefine it. |
| **Layout utilities** — `.flex` `.gap-1` `.mb-2` `.two-col` `.grid-auto` | `css/layout.css`, `css/base.css` | platform only | …use freely. |
| **Tailwind utilities** — `tw-` prefixed | `css/tailwind.built.css` | regenerated by `npm run tw:build` | …use freely — §6 is cleared. Re-run the build + `npm run verify:tw`. |
| **Module body** — this screen's own cards and rows | `modules/<id>/frontend/template.html` | that module | …author freely, from the parts above. |
| **Module-only effect CSS** | `modules/<id>/frontend/<id>.css` | that module | …add *effects and concepts* only (§5). Never restyle a shared component. |

**If you need a change to a shared component, change it in `components.css` —
once, for everybody. Never fork it into a module.**

## 2 · The universal chrome — canonical markup

These are the blocks every screen shares. Copy them verbatim. They are already
theme-aware and responsive; changing a class here changes the whole ERP.

### 2.1 Sidebar nav (platform-rendered — never authored by a module)

Built by `platform/core/app.js` from the registry in `platform/core/config.js`.
A module appears in the nav by being registered there + in its company's
`module.json`. **You do not write nav markup. Ever.**

```html
<!-- REFERENCE ONLY — emitted by app.js. Do not copy into a module. -->
<nav id="nav" class="nav" aria-label="Modules">
  <div class="nav-group">
    <a class="nav-item" href="#/woodart/materials" data-route="woodart/materials">
      <span class="nav-ico"><i class="bi bi-boxes"></i></span>
      <span class="nav-label">Materials</span>
      <span class="nav-caret" role="button"><i class="bi bi-chevron-right"></i></span>
    </a>
    <div class="nav-subs"><div class="nav-subs-inner">
      <a class="nav-sub" href="#/woodart/materials/stock"><span class="nav-sub-dot"></span><span>Stock</span></a>
    </div></div>
  </div>
  <div class="nav-divider" aria-hidden="true"></div>
</nav>
```

Sizing is deliberate and owner-tuned (2026-07-21): `.nav-item` font
`clamp(14.5px,1.75vh,15.5px)`, `.nav-sub` font `clamp(13.5px,1.6vh,14.5px)`,
`.nav` gap `clamp(2px,0.3vh,4px)`. **Do not "improve" these numbers.**

### 2.2 Page head — every screen starts with exactly this

```html
<div data-shell="head" class="page-head">
  <div>
    <h1 class="page-title" data-fill="title"><span class="eyebrow">Woodart › Materials</span><i class="bi bi-boxes"></i></h1>
    <p class="page-sub" title="Wood, laminates, hardware and finishes inventory.">Wood, laminates, hardware and finishes inventory.</p>
  </div>
  <div class="page-actions">
    <a class="btn btn-ghost" href="#/woodart/procurement"><i class="bi bi-cart-fill"></i> Procurement</a>
    <button class="btn btn-primary" data-act="new"><i class="bi bi-plus-lg"></i> New Item</button>
  </div>
</div>
```

Rules that are not negotiable:
- The `<h1>` inner run (`eyebrow` + `<i>`) stays on **one line** — a newline
  clones as a stray text node and shifts pixels.
- `.page-actions` is **always present**, even with no buttons. Views inject into
  it after the fact; a missing rail is a null dereference.
- The title is a **text node after the icon**, matching `EPAL.pageHead`.

### 2.3 Section-tab band

```html
<div data-shell="tabs" class="tab-underline mb-3">
  <button data-tab="stock">Stock</button>
  <button data-tab="movements">Movements</button>
  <button data-tab="valuation">Valuation</button>
</div>
```

Add `tabs-dense` when a module has **7 or more** tabs (Master Accounts = 9,
Finance = 13). The logic marks `.active` and wires navigation; it strips the
`data-tab` hooks after wiring.

### 2.4 KPI strip

```html
<div class="kpi-grid kpi-compact stagger">
  <div class="kpi-card">
    <div class="kpi-top"><span class="kpi-label">Stock Value</span><span class="kpi-ico"><i class="bi bi-wallet2"></i></span></div>
    <div class="kpi-value" data-k="stockValue">—</div>
  </div>
</div>
```

`data-k` is the live-value slot. The HTML ships a `—` placeholder so the screen
reads correctly with JS disabled and never flashes empty.

### 2.5 Card — the universal container

```html
<div class="card">
  <div class="card-head">
    <h3><i class="bi bi-list-columns-reverse"></i> Material Register</h3>
    <span class="card-sub">Every item, live stock and reorder level</span>
  </div>
  <div class="card-body" data-fill="register"></div>
</div>
```

`card-pad` replaces `card-head`+`card-body` for a plain padded card.
`card-foot` for a footer. `card-accent` for the accent-bordered variant.

### 2.6 Data grid, modal, form

Never hand-roll these. They are platform kits and they carry search, sort,
pagination, CSV export, keyboard handling and focus trapping for free:

| Need | Use | Lives in |
|---|---|---|
| Table of records | `EPAL.table({columns, rows, searchKeys, exportName, …})` | `platform/kit/datatable.js` |
| Dialog | `EPAL.ui.modal({title, icon, size, body})` | `platform/core/ui.js` |
| Form / modal form | `EPAL.form(...)` · `EPAL.formModal(...)` | `platform/kit/forms.js` |
| Confirm / toast | `EPAL.ui.confirm(...)` · `EPAL.ui.toast(msg, level)` | `platform/core/ui.js` |
| Chart | `EPAL.charts.bar/line/doughnut(canvas, spec)` | `platform/core/charts.js` |
| Printable document | `EPAL.doc.open({...})` | `platform/engines-library/documents.js` |
| Payment source / cash legs | `EPAL.pay.*` | `platform/kit/cash.js` |

The grid, the modal and the chart are the **only** places JS is allowed to
produce structure (see §4).

## 3 · Data-attribute grammar — the HTML↔JS handshake

The markup is the skeleton; JS reaches into it through **these hooks only**.
Same names in every module of every company, so any developer can read any screen.

| Hook | Means | Used by |
|---|---|---|
| `data-screen="x"` | a whole screen, as plain HTML | `screen('x')` clones it |
| `data-shell="x"` | reusable chrome (head, tabs, switcher) | `shell('x')` clones it |
| `data-fill="x"` | a slot JS drops a built widget into (a grid, a chart) | `node.querySelector('[data-fill="x"]')` |
| `data-k="x"` | a live scalar value slot (a KPI number) | `fillK(node,'x',value)` |
| `data-tab="x"` | a tab button | logic marks `.active`, wires nav, strips the hook |
| `data-act="x"` | a button that performs an action | logic wires `onclick` |
| `data-role="x"` | a named region inside a screen | logic reads/updates it |
| `data-co="x"` | a company-switcher button | switches the scoped company |
| `data-when="empty"` | a block removed when there IS data | logic removes it |

Anything conditional lives in the markup and is **removed** when it does not
apply — never built on demand. That is how a "due this month" banner and a
permission-gated button both work.

## 4 · Where JS is allowed to make DOM

**HTML is the skeleton. JS is muscle and nerves — never bone.**

JS **may** create DOM in exactly these cases:

1. **Live data grids** — `EPAL.table` (row count is data, not layout).
2. **0..N repeated records** — invoice lines, kanban cards, snag rows, action-
   centre rows. Clone a `[hidden]` prototype element that is IN the markup:
   ```html
   <div class="data-list" data-fill="lines">
     <div class="data-row" data-proto="line" hidden>
       <span class="flex-1" data-slot="item"></span>
       <span class="num" data-slot="amount"></span>
     </div>
   </div>
   ```
3. **Computed inline styles** — a progress bar's `width: 63%`, a gradient hue
   derived from a balance.
4. **Charts** — the `<canvas>` is in the markup; Chart.js owns its pixels.
5. **Animation, hover, transitions, effects.**

JS **may not**:
- build a page head, tab band, card, KPI tile, section or banner;
- use `el()` / hyperscript to assemble screen structure;
- use `<template>` fragment-cloning as a screen's structure.

**Forbidden in `template.html`, no exceptions: `<script>` and `<template>`.**
(Owner, 2026-07-27.) The file must open in a browser and *show the screen*.
Repetition uses the `[hidden] [data-proto]` prototype above.

## 5 · Styling method — what goes where

```
1. Design tokens (tokens.css)        →  colour, type, radius, shadow, motion
2. Component classes (components.css)→  what the thing IS   (.card, .btn)
3. Tailwind utilities (tw-)          →  where it SITS + how it LOOKS
                                        (tw-relative, tw-gap-2, tw-max-w-[320px])
4. Module CSS (<id>.css)             →  effects + concepts UNIQUE to this module
5. JS                                →  motion, live values, behaviour
```

Layers 2 and 3 are partners, not rivals: `class="card tw-max-w-[320px]"` — the
component class says *what it is*, the utility says *where it sits*. The legacy
house utilities in `layout.css`/`base.css` (`.flex`, `.gap-1`, `.mb-2`) still
work and still style every unconverted screen; **do not delete them** until every
screen is converted (R4). **All new markup uses `tw-` for utilities.**

> ⚠️ **Convert by VALUE, not by name.** The house scale and Tailwind's default
> scale do not agree. House `.mt-1` is **6px**; Tailwind's `mt-1` is **4px**.
> `.xs` is `--fs-micro` = **11px**; Tailwind's `text-xs` is 12px. A blind rename
> silently shifts pixels on a screen that is supposed to be identical.
> Use an arbitrary value that matches the token — `tw-mt-[6px]`,
> `tw-text-[11px]` — and check `platform/design-system/css/*` for the real
> number before trusting any mapping. Verified-exact pairs so far:
>
> | House | Tailwind | Value |
> |---|---|---|
> | `.flex-1` | `tw-flex-1` | `flex: 1 1 0%` |
> | `.fw-600` | `tw-font-semibold` | `600` |
> | `.mt-1` | `tw-mt-[6px]` | `6px` (**not** `tw-mt-1`) |
> | `.xs` | `tw-text-[11px]` | `--fs-micro` (**not** `tw-text-xs`) |
> | `.text-mute` | `tw-text-ink-mute` | `var(--text-mute)` |
> | `.text-muted` | `tw-text-ink-dim` | `var(--text-dim)` |
>
> The colour utilities resolve to `var()` references, so they stay correct in
> both themes and under any company accent — that is why the config maps colour
> roles to variables instead of frozen hexes.

Module CSS is for **custom effects and concepts only** — a bespoke gradient
thumbnail, a scene-specific keyframe, a `::before` a utility cannot express. It
may **never** restyle `.card`, `.btn`, `.page-head` or any shared class. Prefix
every module rule with a module-owned namespace (`.wa-mat-…`), exactly as
Travels expenses uses `.tv-exp-…`.

**Never hard-code a colour.** Use `var(--accent)`, `var(--text-mute)`,
`var(--surface-2)`, `var(--border-strong)`. Both themes then work for free.
The one legitimate hard-coded colour is a **company accent** or a **status
colour map** declared once as a JS constant at the top of the module.

## 6 · Tailwind — ✅ UNLOCKED (2026-07-27), and permanently gated

Tailwind is **prefixed `tw-`** and seeded from the real `tokens.css`. It was
deferred because `npm run tw:build` was believed not to reproduce the committed
`tailwind.built.css` losslessly — dropping arbitrary-value classes
(`tw-max-w-[320px]`…) and silently breaking untouched screens.

**That is resolved. Measured, not assumed:**

| Check | Result |
|---|---|
| Fresh build vs committed CSS | **byte-identical** — md5 `fa2b2623…`, 577 bytes |
| Verified on | tailwindcss **3.4.17 and 3.4.19** — both produce the same bytes |
| `tw-` class literals in the app | **17**, every one present in the built CSS |
| Classes composed dynamically in JS | **zero** — the original fear does not occur |

The one real risk left was *drift over time*, so it is now enforced by a gate
instead of a promise:

```bash
npm run verify:tw          # tools/verify/tailwind.mjs
```

- **Check A · REPRODUCIBLE** — a fresh build must be byte-identical to the
  committed file. Catches a hand-edited CSS or a changed compiler.
- **Check B · NO ORPHANS** — every `tw-` class used anywhere must have a rule in
  the committed file. Catches *"added a class, forgot `tw:build`"* — the failure
  that actually ships broken pixels, because production is a static git-pull.

Both were proven to go **red** on an injected bad class and green again after
(self-tested 2026-07-27). The version is pinned **exactly** (no caret) in
`package.json`, and `safelist` is documented in the config and intentionally
empty (§ config comments explain when an entry is justified).

### The rules for writing `tw-` classes

1. **Never compose a class name.** `'tw-max-w-[' + w + 'px]'` is invisible to the
   scanner. Switch between whole literals instead:
   `wide ? 'tw-max-w-[320px]' : 'tw-max-w-[180px]'`.
2. **A genuinely computed value is not a utility** — a percentage bar width, a
   derived hue — set it as an inline style (§4.3).
3. **Run `npm run tw:build` then `npm run verify:tw` before committing** any
   screen that introduces a new class, and commit the regenerated CSS with it.

House component classes (`.card`, `.btn`, `.kpi-card`) remain the vocabulary for
*what a thing is*; Tailwind is for *where it sits and how it looks*. Both are
first-class — see §5.

## 7 · Verification — a screen is not done until

```bash
npm run verify:tw                         # tailwind gate — reproducible + no orphan classes
node tools/verify/sweep.mjs both          # 222 routes, 0 console errors, both themes
node tools/verify/parity.mjs shoot .parity/<mod>-before <routes> both
node tools/verify/parity.mjs diff .parity/<mod>-before .parity/<mod>-after
```

- **Rebuilding an existing screen** → the diff must be byte-identical (light
  byte-perfect, dark ≤ AA jitter). Shoot before/after **back-to-back in one
  sitting** — `.parity` baselines drift because the harness accumulates
  localStorage between runs.
- **A brand-new screen** → no baseline exists; the gate is sweep-clean in both
  themes plus a visual read against this contract.
- A **DOM dump** (`#view` innerHTML, hooks normalised) is a stronger proof than
  pixels for markup work — it catches structure the 1440×900 fold never shows.

## 8 · Adding something genuinely new to the shared vocabulary

If a module needs a component that does not exist here (say a "material swatch"),
and a second module will plausibly need it too:

1. Add the class to `platform/design-system/css/components.css`, themed for
   light **and** dark, using tokens only.
2. Add its canonical markup to §2 of this file.
3. Add its name to the §2.8 inventory.
4. Re-sweep both themes.

That is the *only* sanctioned way the shared vocabulary grows. One place, one
definition, everywhere at once.
